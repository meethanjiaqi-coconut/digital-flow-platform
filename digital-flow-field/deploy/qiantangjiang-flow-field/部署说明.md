# 钱塘江数字流场后端部署说明

## 1. 交付内容

本包用于在河口院正式部署 DAT 转换脚本之前，先把数字流场后端和一场真实转换数据部署到钱塘江空间数据管理平台环境，供定川进行接口联调。

| 文件或目录 | 用途 |
|---|---|
| `sgxt-flow-field.tar` | Maven assembly 生成的 Portainer 构建上下文，根目录只有 Dockerfile、entrypoint.sh 和服务 JAR |
| `Dockerfile`、`entrypoint.sh` | 与 `ywgl-model-oauth2.tar` 的文件内容对齐，仅服务 JAR 名和端口不同 |
| `docker-compose.yml` | Portainer Stack 或命令行 Compose 配置 |
| `.env.example` | 宿主机端口和持久卷目录模板 |
| `server.env.example` | PostgreSQL、Nacos、发布令牌和服务参数模板 |
| `nginx-flow-field.conf` | 钱塘江现有 9091 nginx 的反向代理片段 |
| `publisher/` | Python 发布工具、依赖和一场真实转换示例数据 |
| `SHA256SUMS.txt` | 交付物完整性校验值 |

示例数据是前端渲染格式，不包含河口院原始 DAT。它包含 72 帧、38,081 个节点、71,958 个单元，约 17 MiB。数据通过发布接口写入 PostgreSQL 元数据和持久卷，不能直接复制进持久卷目录。

## 2. 部署前准备

需要准备：

1. Linux/amd64 Docker 或 Portainer 环境，并能使用钱塘江现有的 `java:8` 基础镜像（本机缓存、私有仓库或镜像加速源均可）。
2. 一个 PostgreSQL 数据库和账号。首次启动时服务会创建 `flow_field` schema 及相关表，因此账号需要相应 DDL 权限。
3. 服务器本机 SSD 目录，建议 `/home/data/flow-field`；不要把高频读取数据长期放在 `/home/images/web_home` 静态发布目录。
4. 服务器防火墙仅向钱塘江内网、河口院发布机和运维机开放 8793。
5. 一个至少 32 位的随机 `FLOW_PUBLISH_TOKEN`。令牌不要写入文档、代码仓库或 nginx 配置。

当前阶段 Nacos 可以关闭。后续接入 Nacos 时，先向平台维护人员确认 Namespace ID、Group、Data ID、profile 和访问账号；建议 Data ID 使用 `sgxt-flow-field-prod.yml`，Group 使用平台统一值。

## 3. 在 Portainer 构建镜像

按照钱塘江现有部署手册，可先把交付包临时上传到服务器发布目录，完成后应转移到非 Web 目录或删除，避免镜像包被静态访问。

`sgxt-flow-field.tar` 与 `ywgl-model-oauth2.tar` 类型一致，是 Docker 构建上下文，不是
`docker save` 镜像归档。因此不要使用 Images → Import，也不能执行 `docker load`。

在 Portainer 中操作：

1. 打开 **Images → Build a new image**。
2. Name 填写 `sgxt-flow-field:1.0.1`。
3. Build method 选择 **Upload**，上传 `sgxt-flow-field.tar`。
4. Dockerfile path 填写 `Dockerfile`。
5. 点击 **Build the image**。构建日志应能看到复制 `sgxt-flow-field.jar` 和暴露 8793 端口。

命令行构建方式：

```bash
mkdir -p /tmp/sgxt-flow-field-build
tar -xf sgxt-flow-field.tar -C /tmp/sgxt-flow-field-build
docker build -t sgxt-flow-field:1.0.1 /tmp/sgxt-flow-field-build
docker image inspect sgxt-flow-field:1.0.1 --format '{{.Os}}/{{.Architecture}}'
```

最后一条命令应输出 `linux/amd64`。若构建在 `FROM java:8` 处失败，说明目标服务器未缓存
该基础镜像且当前镜像源无法拉取；请按 OAuth2 服务现有的方式配置相同基础镜像来源后重试。

## 4. 配置并启动

在服务器创建部署目录并复制模板：

```bash
mkdir -p /home/apps/sgxt-flow-field
mkdir -p /home/data/flow-field
cd /home/apps/sgxt-flow-field
cp .env.example .env
cp server.env.example server.env
chmod 600 server.env
```

编辑 `.env`：

```env
FLOW_HOST_PORT=8793
FLOW_DATA_HOST_DIR=/home/data/flow-field
```

编辑 `server.env`，至少填写以下四项：

```env
PG_URL=jdbc:postgresql://实际PG地址:5432/实际数据库名
PG_USER=实际账号
PG_PASSWORD=实际密码
FLOW_PUBLISH_TOKEN=至少32位随机令牌
```

首次联调建议保持 `NACOS_ENABLED=false`。配置完成后启动：

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=200 sgxt-flow-field
```

Portainer Stack 部署时，将 `docker-compose.yml` 内容粘贴到 Editor，并在 Stack 环境变量中配置 `FLOW_HOST_PORT`、`FLOW_DATA_HOST_DIR`；`server.env` 应通过受控文件或 Portainer 环境变量维护。若钱塘江已经用 Stack 管理该容器，后续更新应继续修改 Stack，避免直接 Duplicate/Edit 后被 Stack 定义覆盖。

## 5. 服务健康检查

在服务器本机执行：

```bash
curl http://127.0.0.1:8793/flow-field/actuator/health
```

预期返回包含 `"status":"UP"`。若启动失败，优先检查 PostgreSQL 地址、账号 DDL 权限和持久卷写权限：

```bash
docker compose logs --tail=300 sgxt-flow-field
ls -ld /home/data/flow-field
```

## 6. 发布随包示例数据

推荐在开发机或运维机执行发布，不要求服务器安装 Python。发布机需要 Python 3.9+，并且能访问服务的 8793 端口。

Windows PowerShell：

```powershell
python -m pip install -r .\publisher\requirements-flowfield.txt
$env:FLOW_PUBLISH_TOKEN = '与 server.env 完全一致的令牌'
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File .\publisher\publish-sample-data.ps1 `
  -Server 'http://服务地址:8793/flow-field'
Remove-Item Env:FLOW_PUBLISH_TOKEN
```

Linux：

```bash
python3 -m pip install -r publisher/requirements-flowfield.txt
export FLOW_PUBLISH_TOKEN='与 server.env 完全一致的令牌'
sh publisher/publish-sample-data.sh 'http://服务地址:8793/flow-field'
unset FLOW_PUBLISH_TOKEN
```

脚本会先校验数据包，再以 4 并发上传网格和 72 帧，失败最多重试 5 次。中断后重新执行同一命令即可续传；相同 `sourceRunId` 重复发布是幂等的。

## 7. 验证数据接口

先查看可用场次和最新场次：

```bash
curl http://127.0.0.1:8793/flow-field/api/v1/scenarios
curl http://127.0.0.1:8793/flow-field/api/v1/scenarios/latest/manifest
```

场次发布成功后，状态应为 `READY`，Manifest 中应为 72 帧。前端使用的主要接口如下：

| 接口 | 用途 |
|---|---|
| `GET /flow-field/api/v1/scenarios` | 获取最近 100 个可用场次 |
| `GET /flow-field/api/v1/scenarios/latest/manifest` | 获取最新场次清单 |
| `GET /flow-field/api/v1/scenarios/{id}/manifest` | 获取指定场次清单 |
| `GET /flow-field/api/v1/meshes/{meshId}` | 获取 gzip 网格二进制 |
| `GET /flow-field/api/v1/scenarios/{id}/frames/{index}` | 获取 gzip 单帧二进制 |
| `GET /flow-field/api/v1/scenarios/{id}/cells/{cellIndex}/series` | 获取单元 72 时次过程线 |

浏览器会依据 `Content-Encoding: gzip` 自动解压，前端拿到的是原始 `ArrayBuffer`。不要在 axios/fetch 中再次手工 gunzip。

## 8. 接入钱塘江 nginx

把 `nginx-flow-field.conf` 放入现有 9091 端口的 `server { ... }` 内，将 `<FLOW_FIELD_SERVER_HOST>` 替换为服务实际地址，然后检查并重载 nginx：

```bash
nginx -t
nginx -s reload
```

如果 nginx 在容器中，使用现有 nginx 容器名执行 `docker exec`。代理验证：

```bash
curl http://钱塘江平台地址:9091/flow-field/api/v1/scenarios
```

配置片段会阻断 `/flow-field/internal/`，因此示例数据和河口院后续数据发布应从受信网络直连 8793。只读接口虽然由服务校验内网来源，平台边界仍必须由防火墙/nginx 访问策略承担。

定川集成前端时设置：

```env
VITE_FLOW_API_BASE=/flow-field
```

这样浏览器与钱塘江平台同域访问，不需要额外处理 CORS。

## 9. 数据与容量

持久卷只保存前端所需 gzip 网格和帧，不保存原始 DAT。相同网格的场次共享网格文件；默认只保留最近 100 个 `READY` 场次，超出后最旧场次转为 `ARCHIVED` 并删除帧文件，PostgreSQL 元数据继续保留。

当前规模估算：

- 一场压缩帧约 15.6 MiB。
- 共享网格约 1.3 MiB。
- 100 场约 1.53 GiB，加暂存和运行余量后建议至少预留 5 GiB SSD 空间。

## 10. 更新与回滚

更新镜像时导入新标签，并修改 Stack/Compose 中的 `image`。不要删除 `/home/data/flow-field`，也不要更改原有 PostgreSQL 数据库。

回滚步骤：

1. 将 `image` 改回上一版本标签。
2. 执行 `docker compose up -d` 或 Portainer 的 Update the stack。
3. 验证 actuator、场次列表和一帧二进制请求。

镜像升级和数据持久卷互相独立，因此正常回滚不会丢失已发布场次。
